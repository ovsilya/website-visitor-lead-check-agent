How the MDL app gets deployed: GitHub → Terraform → CI/CD → GCP

No one changes the Marketing projects by hand. Every change is code in GitHub, reviewed in a pull request by the platform reviewers, then applied by a robot (the pipeline) using a service account. Two repos, two lanes: the infrastructure (what exists in the project) and the app (the code that runs on it).
NP marketing-np · Prod marketing-prod · Infra repo tf-infra-marketing · App repo mdl-lead-check (company org, to create) · App on Cloud Run behind IAP · Today's MVP: lab lab-project

CI vs CD

  • CI (continuous integration): a robot checks the change: tests, terraform plan.
  • CD (continuous delivery/deployment): a robot ships it: terraform apply, build, release.
  • Here the robot is Cloud Build in the NP project, not GitHub Actions. It's started by git tags, not by PRs: a .plan tag runs plan and a .v tag runs apply. The triggers already exist.
  • App lane, suggested: a Cloud Build trigger on the app repo, same as the infra repo. No keys and no WIF needed. GitHub Actions would need WIF instead. Agree with platform lead.

Who's allowed to do what

  • You: read the project, write code, open PRs. Not Owner.
  • iac-sa: the Terraform robot. Powerful: creates and changes resources.
  • cicd-sa: the release robot. Deploys new app versions only.
  • The app's own SA (e.g. mdl-agent-run): only Vertex AI User + Logs Writer.
  • Never act as iac-sa yourself; that skips the review.

How GitHub and GCP connect here

  • Not WIF: GCP pulls from GitHub. Cloud Build's GitHub connection (a GitHub App) watches the repo for tags and runs the build inside GCP as iac-sa.
  • No keys on GitHub. Cloud Build reads company modules with a deploy key kept in Secret Manager.
  • The factory already did this, so no bootstrap is needed. WIF (the platform team's bootstrap, a WIF module) is only for GitHub Actions pipelines.
